# AI 知识图谱与聊天机器人方案

## 1. 方案定位

本方案对应仓库中的“知识图谱 + 智能问答”能力，目标是把结构化调研数据转化为可检索、可对比、可解释的知识服务。

当前实现分为两层：

- 知识图谱层：将 `parks`、`sites`、`indicators`、`scores` 等关系写入 Neo4j
- 问答层：通过 `RAGEngine` 组合关系库上下文、可选向量检索和本地规则式回答

## 2. 现状说明

当前代码已经具备以下能力：

- `/api/chat` 问答接口
- `/api/kg/*` 图谱查询接口
- `scripts/build_kg.py` 图谱构建脚本
- 前端聊天页面和知识图谱页面

需要特别说明的是：

- `AI_PROVIDER` 目前更多是预留配置位，现有 `RAGEngine` 仍以本地规则式回答为主
- `NEO4J_ENABLED=true` 才会启用 Neo4j 连接；未启用时图谱接口会回退到关系库侧统计
- `stream_query()` 已预留，但当前聊天接口使用的是同步返回模式

## 3. 知识图谱构建链路

### 3.1 数据来源

- PostgreSQL 或 SQLite 中的结构化业务数据
- 主要表：`parks`、`sites`、`indicators`、`scores`、`exhibitions`

### 3.2 构建脚本

`backend/scripts/build_kg.py` 的职责是：

1. 读取关系库中的公园和评分数据
2. 创建图数据库约束
3. 构建节点和边
4. 输出图谱统计信息

### 3.3 节点类型

当前脚本会构建或使用以下节点：

- `Park`
- `Site`
- `Indicator`
- `ParkType`
- `Province`
- `City`
- `Batch`
- `HistoricalPeriod`
- `Dimension`
- `Museum`
- `MediaSystem`

### 3.4 关系类型

当前脚本中使用的主要关系如下：

| 关系 | 含义 |
|------|------|
| `HAS_TYPE` | 公园属于某一类型 |
| `LOCATED_IN` | 公园位于某省或某市 |
| `BELONGS_TO_BATCH` | 公园属于某一批次 |
| `CONTAINS` | 公园包含遗址点 |
| `BELONGS_TO` | 遗址点属于某时期 / 指标属于某维度 |
| `HAS_SCORE` | 公园与指标之间的评分关系 |
| `HAS_MUSEUM` | 公园与博物馆关系 |
| `HAS_MEDIA` | 公园与传播媒介关系 |
| `SIMILAR_TYPE` | 同类型公园之间的相似关系 |
| `SAME_REGION` | 同区域公园之间的关系 |

### 3.5 构建前提

在当前仓库中，如果需要真正执行图谱构建脚本，请确保：

- Neo4j 服务可用
- `NEO4J_ENABLED=true`
- `NEO4J_URI`、`NEO4J_USER`、`NEO4J_PASSWORD` 配置正确

否则 `build_kg.py` 会因图数据库连接为空而无法完成构建。

## 4. 图谱查询接口

`backend/app/api/kg.py` 目前提供以下接口：

| 接口 | 作用 |
|------|------|
| `GET /api/kg/stats` | 图谱节点与关系统计 |
| `GET /api/kg/entity/{entity_type}` | 查询指定实体列表 |
| `GET /api/kg/entity/{entity_type}/{name}` | 查询实体详情与关系 |
| `GET /api/kg/neighbors/{name}` | 查询邻居节点和路径 |
| `GET /api/kg/search?q=...` | 图谱搜索 |

说明：上述接口均依赖 JWT 登录态。

### 4.1 降级策略

当 Neo4j 不可用时，接口会回退到关系库逻辑：

- `stats` 返回基于 SQL 聚合的节点/关系统计
- `entity` 和 `search` 使用 `parks`、`indicators` 等表做模糊查询
- `neighbors` 使用公园类型和评分关系构造轻量图结果

## 5. 聊天机器人链路

### 5.1 前端调用

`frontend/src/views/Chat.vue` 通过 `/api/chat` 提交：

```json
{
  "message": "请对比圆明园和大明宫",
  "conversation_id": ""
}
```

### 5.2 后端流程

`backend/app/api/chat.py` 的处理顺序如下：

1. 校验 JWT 登录态
2. 获取或创建 `conversation_id`
3. 将请求交给 `RAGEngine`
4. 记录对话历史
5. 返回答案、来源和图表数据

返回字段包括：

- `message`
- `conversation_id`
- `sources`
- `chart_data`

当前对话历史保存在内存字典中，单个会话最多保留最近 20 条消息。

### 5.3 `RAGEngine` 处理逻辑

`backend/app/services/rag_engine.py` 当前采用本地可解释链路：

1. 意图识别：根据关键词判断是否是对比、统计、列表、评分或事实类问题
2. 数据库检索：从关系库中提取公园、指标和得分上下文
3. 向量检索：如果 ChromaDB 可用，则补充相关文档片段
4. 上下文拼装：把结构化数据和文档片段合并为上下文
5. 回答生成：使用本地规则式回答模板返回结果

### 5.4 当前支持的问答类型

- 基本信息查询
- 某公园评分与维度结果查询
- 多公园对比
- 公园列表查询
- 基于关键词的雷达图可视化结果

### 5.5 图表返回格式

当问题命中对比意图且识别到多个公园时，后端可能返回如下结构：

```json
{
  "type": "radar",
  "data": [
    {
      "name": "圆明园",
      "values": {
        "遗址保护效能": 60,
        "文化传播效能": 80
      }
    }
  ]
}
```

前端会根据该结构渲染雷达图。

## 6. 回答策略与降级

### 6.1 正常路径

- 结构化数据足够时，优先返回数据库中的明确结论
- 对比类问题优先返回可视化数据
- 列表类问题优先返回完整列表

### 6.2 降级路径

- 没有命中具体公园时，返回已收录公园列表
- 没有启用 ChromaDB 时，只使用结构化上下文
- 外部大模型不可用时，继续返回本地模板式结果

### 6.3 当前限制

- 现有实现没有真正调用外部 LLM API
- `AI_PROVIDER` 和 API Key 目前属于预留配置，不是当前问答链路的必需项
- 聊天历史存在于内存字典中，服务重启后会丢失

## 7. 推荐接入顺序

如果后续要把问答能力进一步产品化，建议按以下顺序演进：

1. 先稳定数据导入和评分体系
2. 再把 Neo4j 构图流程跑通
3. 然后接入真实大模型
4. 最后再增强流式输出、引用溯源和复杂图表
