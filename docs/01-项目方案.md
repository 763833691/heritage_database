# 国家考古遗址公园调研数据平台项目方案

## 1. 项目背景

国家考古遗址公园的调研资料通常分散在 Word、Excel、图片、网页评论和地理数据中，存在以下问题：

- 数据格式不统一，难以快速检索和复用
- 评分、问卷、评论、空间与设施信息之间缺少关联
- 跨公园对比需要人工整理，效率低
- 调研成果难以沉淀为可检索、可问答、可分析的知识资产

本项目的目标，是把调研资料整理为统一的数据平台，并在此基础上提供统计分析、知识图谱和智能问答能力。

## 2. 建设目标

1. 建立统一的数据存储与管理体系
2. 支持遗址公园、遗址点、评分、问卷、评论等多源数据管理
3. 支持按公园、类型、省份、维度进行统计与对比分析
4. 支持知识图谱构建、实体检索和关系查询
5. 支持面向调研数据的智能问答与可视化输出
6. 支持本地开发与 Docker 部署两种使用方式

## 3. 当前实现范围

仓库当前已经具备以下能力：

- FastAPI 后端服务
- Vue 3 前端管理界面
- PostgreSQL / SQLite 双数据库支持
- 遗址公园、评分、问卷、评论等 ORM 模型
- 数据总览、维度对比、雷达图统计接口
- Chatbot 问答接口与本地 RAG 引擎
- Neo4j 图谱构建脚本与图谱查询接口
- Docker Compose 部署文件

说明：

- 当前代码默认支持本地规则式回答，外部大模型接口属于预留扩展位
- Neo4j 为可选能力，未启用时图谱相关接口会自动回退到关系数据库侧的统计结果

## 4. 技术路线

| 模块 | 选型 | 说明 |
|------|------|------|
| 前端 | Vue 3 + Element Plus + ECharts + Leaflet | 负责管理、统计、地图和问答页面 |
| 后端 | FastAPI + SQLAlchemy + Pydantic | 提供 REST API、认证和数据访问 |
| 主数据库 | PostgreSQL | Docker 和部署场景优先推荐 |
| 本地数据库 | SQLite | 单机调试和轻量演示可用 |
| 图数据库 | Neo4j | 用于知识图谱和实体关系查询 |
| 向量库 | ChromaDB | 用于后续文档语义检索扩展 |
| AI 能力 | LangChain + DashScope/OpenAI 配置 | 现阶段以本地规则式 RAG 为主 |
| 部署 | Docker Compose + Nginx | 统一启动和反向代理 |

## 5. 系统数据流

### 5.1 数据进入

1. 原始资料进入：Word、Excel、图片、网页评论、地理信息
2. 初始化脚本导入：`scripts/init_db.py`
3. 人工补录与批量导入：管理端上传 Excel 或手工编辑
4. 结构化落库：写入 PostgreSQL / SQLite

### 5.2 数据分析

1. 前端发起统计或对比请求
2. 后端通过 ORM 聚合查询
3. 返回总览、维度得分、雷达图或明细列表

### 5.3 知识图谱

1. `scripts/build_kg.py` 从关系库读取结构化数据
2. 生成 Park、Site、Indicator 等节点及其关系
3. 写入 Neo4j，支持实体、邻居和搜索查询
4. 未启用 Neo4j 时，图谱接口回退到 SQL 结果

### 5.4 AI 问答

1. 前端 `Chat.vue` 调用 `/api/chat`
2. 后端鉴权后进入 `RAGEngine`
3. 根据关键词判断意图，查询数据库和可选向量库
4. 组装上下文并生成回答
5. 对比类问题可附带雷达图数据

## 6. 功能边界

### 6.1 已纳入范围

- 遗址公园基础信息管理
- 遗址点信息管理
- 评分数据管理
- 问卷和问卷答案管理
- 网络评论管理
- 展示利用、区位、教育活动、社区共建数据管理
- 数据总览与维度对比分析
- 知识图谱查询
- AI 助手问答
- 管理员账号与权限控制

### 6.2 预留扩展

- 更完整的文档解析与 OCR 流程
- 真实大模型调用与提示词编排
- 更复杂的空间分析能力
- 多租户和细粒度权限体系
- 自动报告生成与导出

## 7. 部署形态

### 7.1 开发模式

- SQLite 可直接运行
- 适合本地调试和快速验证
- 前后端分开启动

### 7.2 部署模式

- PostgreSQL + Neo4j + FastAPI + Vue 3
- Docker Compose 统一编排
- Nginx 负责反向代理和静态资源
- 适合演示、课程答辩和后续持续迭代
